# Scanly: архитектура и план MVP

Версия 0.2, 8 октября 2026. Документ к шагам 1–8 из п.14 ТЗ. Кода пока нет, реализация стартует после подтверждения.

---

## 0. Что изменилось в v0.2

Вводные от Ярослава:

1. **Запуск в России.**
2. **Партнёров нет**, базу товаров и цен нужно собирать самим, и она должна быть большой.
3. **Минимальные вложения.** AI сейчас скорее приманка и часть масштабирования, а не фундамент MVP.

Что из этого следует:

- **AI уходит из MVP.** Модель данных и место в карточке остаются, блок включается фича-флагом, когда наберётся достаточно отзывов. На старте карточку держат рейтинг, распределение оценок и самые полезные отзывы. Подробности в разделе 6.
- **Claude API заменяется российским провайдером** (YandexGPT или GigaChat) за тем же интерфейсом `AiProvider`. Claude из России официально недоступен, а данные пользователей лучше не гонять за рубеж.
- **Данные становятся главным направлением работы.** Появился раздел 11 про сбор базы товаров, магазинов и цен без партнёров.
- **Инфраструктура ужимается до одного сервера в России**: PostgreSQL + API + воркеры в Docker на одной VPS, очереди на самом Postgres (pg-boss) вместо Redis, фото в российском S3. Это закрывает 152-ФЗ и стоит порядка нескольких тысяч рублей в месяц (раздел 12).
- **Вход:** код на email (бесплатно), VK ID, Яндекс ID и Sign in with Apple (обязателен на iOS, если есть вход через сторонние сервисы). SMS-коды и Google убраны: SMS стоят денег, Google в России почти не нужен.
- **Аналитика и краши:** AppMetrica (бесплатно, российская) вместо PostHog.
- **Сторы:** кроме App Store и Google Play добавляется RuStore. Публикация в App Store из России требует отдельной проработки (раздел 10).

## 1. Анализ задачи

Продукт отвечает на один вопрос: **стоит ли брать этот товар**. Всё остальное работает на скорость ответа.

Из этого вытекает несколько вещей, которые сильнее всего влияют на архитектуру:

1. **Время от скана до вердикта.** Пользователь стоит у полки. Цель: карточка с ценой и рейтингом за ~1 секунду после считывания кода. Значит, карточка собирается одним запросом, AI-резюме считается заранее (асинхронно), а не в момент скана.
2. **Данные важнее интерфейса.** Сканер и красивая карточка бесполезны, если по штрихкоду ничего не нашлось или цены месячной давности. Самые рискованные части продукта: база товаров и источники цен. Архитектура должна позволять подключать источники данных как адаптеры, не трогая остальной код.
3. **Доверие.** Отзывы без защиты от накруток и AI, который выдумывает, убивают продукт. Отсюда: модерация и антиспам с первого дня, а AI-резюме строится только по реальным отзывам со ссылками на них.
4. **Офлайн-магазин = плохая связь.** В торговых залах часто слабый интернет. Нужны кэш, понятные состояния загрузки и ошибок, повторные запросы.
5. **Монетизация закладывается в модель, но не в MVP.** Партнёрские ссылки появляются сразу (поле у цены), реклама и продвижение позже, но модель данных сразу умеет помечать спонсорский контент.

### Основной сценарий в терминах системы

```
Камера → штрихкод (на устройстве) → GET /products/by-barcode/{code}
       → карточка: товар + лучшая цена + рейтинг + AI-резюме (всё уже посчитано)
       → GET /products/{id}/prices?lat&lng → сравнение
       → переход по affiliate-ссылке (через трекинг-редирект)
```

Если код не найден: состояние «не нашли товар» с переходом в ручной поиск.

## 2. Стек

### Мобильное приложение: React Native + Expo (TypeScript)

Для MVP выбираю кроссплатформу. Почему:

- **Одна кодовая база на iOS и Android.** Для MVP это примерно в 1.7–2 раза меньше работы и одна команда вместо двух.
- **Нативной специфики почти нет.** Тяжёлое тут: камера и сканирование. Обе задачи закрываются нативными модулями (под капотом AVFoundation на iOS и ML Kit на Android), так что скорость сканирования такая же, как в нативном приложении.
- **New Architecture (Fabric, TurboModules) по умолчанию**, производительность списков и анимаций уже не проблема для такого типа UI.
- **Expo закрывает инфраструктуру:** сборки в облаке (EAS Build), публикация в сторы (EAS Submit), OTA-обновления для быстрых фиксов (EAS Update), push-уведомления, шрифты, локализация.
- **Один язык с бэкендом.** TypeScript везде, общие схемы и типы API в одном пакете.

Почему не Flutter: он тоже подходит, но экосистема RN шире по готовым библиотекам (сканер, аналитика, платёжные и партнёрские SDK), и общий TypeScript с бэкендом даёт реальную экономию на типах. Почему не натив: двойная стоимость без выигрыша для этого сценария. Если когда-то упрёмся в нативное (например, AR поверх полки), это делается нативным модулем внутри того же приложения.

| Задача | Решение |
|---|---|
| Фреймворк | Expo SDK (последний стабильный), React Native, TypeScript strict |
| Навигация | Expo Router (файловая маршрутизация, deep links из коробки) |
| Камера и штрихкоды | `react-native-vision-camera` с code scanner (EAN-13, EAN-8, UPC-A, UPC-E) |
| Серверное состояние | TanStack Query (кэш, ретраи, офлайн-персист) |
| Локальное состояние | Zustand (мелкое: сессия, настройки, состояние сканера) |
| Формы и валидация | react-hook-form + zod (схемы общие с бэкендом) |
| HTTP-клиент | генерируется из OpenAPI бэкенда (типобезопасный, без ручных DTO) |
| Хранение токенов | `expo-secure-store` (Keychain / Keystore) |
| Геолокация | `expo-location` |
| Изображения | `expo-image` (кэш, плавная загрузка) |
| Анимации | Reanimated |
| Push | `expo-notifications` (APNs + FCM) |
| Аналитика продукта | AppMetrica (бесплатно, данные в России) |
| Ошибки и краши | AppMetrica crashes, позже Sentry при необходимости |
| Тесты | Jest + React Native Testing Library, e2e на Maestro |

### Бэкенд: NestJS + PostgreSQL

| Задача | Решение |
|---|---|
| Фреймворк | NestJS (TypeScript), модульная структура, OpenAPI из кода |
| База | PostgreSQL 16+ с PostGIS (расстояния до магазинов) и pg_trgm (нечёткий поиск) |
| ORM и миграции | Prisma |
| Поиск | MVP: полнотекстовый поиск Postgres (русская морфология) + триграммы. Позже Meilisearch/OpenSearch, когда каталог вырастет |
| Очереди | pg-boss (очереди прямо в Postgres: импорт данных, пересчёт рейтингов, push). Redis добавим, только когда упрёмся в нагрузку |
| Кэш | in-memory в процессе API на старте, Redis позже |
| Файлы | российское S3-совместимое хранилище (Yandex Object Storage, Selectel, Timeweb), загрузка напрямую по presigned URL |
| Авторизация | своя: короткоживущий access JWT + ротируемый refresh-токен; код на email + VK ID + Яндекс ID + Sign in with Apple |
| AI (после MVP) | YandexGPT или GigaChat через свой слой `AiProvider` (провайдер заменяем), structured output по JSON-схеме |
| Модерация контента | на старте правила и стоп-слова + ручная очередь, AI-классификатор позже |
| Наблюдаемость | структурные логи (pino), бесплатный тариф Sentry для бэкенда, простые health-check'и |
| Инфраструктура | одна VPS в России, Docker Compose (Postgres, API, воркер, Caddy с HTTPS), ежедневные бэкапы базы в S3, CI на GitHub Actions |

Почему своя авторизация, а не Firebase/Supabase Auth: нам нужны свои правила антиспама и антинакрутки на уровне аккаунта (лимиты, доверие, привязка устройства), а также контроль над хранением персональных данных. Готовый BaaS здесь скорее мешает. Если важнее скорость старта, можно взять Supabase и переехать позже, но я бы этого не делал.

Почему одна VPS, а не managed-сервисы: на старте нагрузка маленькая, а managed Postgres и Kubernetes в облаке стоят в разы дороже. Всё упаковано в Docker, поэтому переезд на managed-базу или несколько серверов делается без переписывания кода.

Почему не микросервисы: для MVP это лишняя сложность. Делаем **модульный монолит**: модули с чёткими границами, общаются через сервисы и события. Любой модуль (например, AI или импорт цен) потом выносится в отдельный воркер без переписывания.

## 3. Архитектура

```
┌──────────────────────────┐
│   Mobile app (Expo)      │
│  features → shared/api   │
└────────────┬─────────────┘
             │ HTTPS, REST /v1, JWT
┌────────────▼─────────────┐        ┌────────────────────┐
│     API (NestJS)         │───────▶│  pg-boss (очереди  │
│  auth, catalog, prices,  │        │  в Postgres)       │
│                          │        └────────────────────┘
│  reviews, favorites, ... │        ┌────────────────────┐
│                          │──jobs─▶│  Workers           │
└───┬──────────┬───────────┘        │  data-import       │
    │          │                    │  moderation        │
    │          │                    │  price-ingestion   │
    ▼          ▼                    │  rating-recalc     │
┌────────┐ ┌──────────┐             │  notifications     │
│Postgres│ │ S3 + CDN │             └─────────┬──────────┘
│+PostGIS│ │ (фото)   │                       │
└────────┘ └──────────┘          ┌────────────▼───────────┐
                                 │ Внешние: YandexGPT /   │
                                 │ GigaChat (после MVP),  │
                                 │ фиды цен, APNs/FCM     │
                                 └────────────────────────┘
```

API и воркеры живут в одном репозитории и одной кодовой базе, запускаются как разные процессы.

### Модули бэкенда

| Модуль | Ответственность |
|---|---|
| `auth` | вход, токены, сессии, удаление аккаунта |
| `users` | профиль, настройки, предпочтения |
| `catalog` | товары, штрихкоды, категории, бренды, состав, КБЖУ, поиск |
| `stores` | сети, магазины, координаты, поиск рядом |
| `prices` | цены, наличие, история, лучшая цена, импорт из источников |
| `reviews` | отзывы, фото, полезность, жалобы, лимиты |
| `ratings` | агрегаты рейтинга, пересчёт |
| `ai` | резюме отзывов, провайдер LLM, валидация ответов |
| `moderation` | автоматические проверки, очередь ручной модерации, санкции |
| `favorites` | избранное |
| `alerts` | подписки на снижение цены (архитектурно в MVP, фича после) |
| `recommendations` | подборки для главного экрана, позже персональные |
| `notifications` | push-токены устройств, отправка |
| `affiliate` | трекинг-редиректы на магазины, учёт переходов |
| `media` | presigned upload, обработка изображений |
| `analytics` | серверные события (скан, переход в магазин) |

### Ключевые решения

- **Карточка товара одним запросом.** `GET /products/by-barcode/{code}` и `GET /products/{id}` возвращают сразу: товар, лучшую цену рядом, агрегат рейтинга, готовое AI-резюме и признак избранного. Отдельные экраны (все цены, все отзывы) догружают своё пагинацией.
- **AI считается заранее.** Новый отзыв ставит задачу в очередь, резюме пересчитывается с дебаунсом (например, при +N новых отзывов или раз в сутки). Скан никогда не ждёт LLM.
- **Источники цен как адаптеры.** Интерфейс `PriceSource` (партнёрский фид, ручной импорт CSV, цена из отзыва пользователя). Каждая цена хранит источник и время, поэтому в UI честно показываем «обновлено 2 часа назад».
- **Партнёрские переходы через свой редирект** (`/go/{priceId}`): считаем клики, подставляем UTM и партнёрские параметры, не храним их в приложении.
- **Спонсорский контент помечен на уровне данных** (`is_sponsored` / отдельная сущность Placement позже), клиент не может показать его без метки.
- **Версионирование API** (`/v1`) и минимальная поддерживаемая версия приложения (force update), потому что мобильные клиенты обновляются медленно.
- **Конфигурация через env и remote config**, никаких хардкодов URL, ключей, лимитов и порогов в коде.

### Схема связей

```

User 1──* Favorite *──1 Product
User 1──* PriceAlert *──1 Product
User 1──* Recommendation *──1 Product

```

### Сущности

Типы условные (Postgres). У всех: `id uuid`, `created_at`, `updated_at`.

**User**
| Поле | Тип | Заметки |
|---|---|---|
| email | text, unique, nullable | или вход через внешний провайдер |
| display_name | text | |
| avatar_url | text? | |
| role | enum `user, moderator, admin` | |
| status | enum `active, shadow_banned, banned, deleted` | shadow ban для спамеров |
| trust_score | int | основа антинакрутки, позже репутация |
| home_location | geography(Point)? | для «рядом» без запроса геолокации |

### Антиспам и антинакрутка (на уровне данных и правил)

- Отзыв можно оставить только после подтверждения аккаунта; новый аккаунт проходит премодерацию первых N отзывов.
- Лимиты: отзывов в сутки на пользователя, жалоб, голосов «полезно»; rate limit на уровне API по пользователю, устройству и IP.
- Один отзыв на товар от пользователя, голосовать за свой отзыв нельзя.
- Автопроверки в очереди: дубли текста, ссылки и контакты, мат и токсичность (AI-классификатор), подозрительные всплески оценок у одного товара.
- Вес отзыва в `weighted_score` зависит от `trust_score` автора; у новых и подозрительных аккаунтов вес ниже.
- Набор жалоб скрывает отзыв до ручной проверки.

## 6. AI-анализ отзывов

> **После MVP.** Раздел описывает, как это будет устроено, когда включим. В MVP строится только модель данных и место в карточке под фича-флагом.

Как гарантируем, что AI не выдумывает:

1. В модель уходят **только опубликованные отзывы** товара (текст, оценка, id), без внешних знаний о товаре.
2. Ответ строго по JSON-схеме: резюме, плюсы, минусы, темы. **Каждый плюс и минус обязан ссылаться на id отзывов**, где он упомянут.
3. Бэкенд валидирует ответ: id существуют, упоминаний не меньше порога, иначе пункт выкидывается. Невалидный ответ = повтор или статус `failed`, старое резюме остаётся.
4. **Порог данных:** меньше N отзывов (например, 5, настраивается) = статус `insufficient_data`, в UI честное «пока мало отзывов для анализа».
5. В UI рядом с резюме видно, по скольким отзывам оно сделано, по тапу на плюс открываются отзывы, где это сказано.
6. Модель и версия промпта сохраняются, промпты лежат в коде и тестируются на фикстурах.

Провайдер: YandexGPT Lite или GigaChat Lite (для резюме хватает лёгкой модели, это копейки на товар). Данные не уходят за пределы России. Доступ через интерфейс `AiProvider`, так что смена провайдера не затрагивает бизнес-логику. Большие объёмы отзывов: отбор репрезентативной выборки (свежие + самые полезные + равномерно по оценкам) и map-reduce по чанкам.

Персональные рекомендации (п.5.6 ТЗ) идут после MVP, модель `Recommendation` и сбор событий для них закладываются сразу.

Минимально нужное сверху (иначе не выпустить): экран настроек с выходом и удалением аккаунта, политика конфиденциальности, согласие на обработку персональных данных, запросы разрешений камеры и геолокации с понятными объяснениями, AppMetrica с ключевыми событиями.

**После MVP, но архитектурно готово:** AI-резюме отзывов, onboarding, магазины рядом как отдельный экран с картой, уведомления о снижении цены, персональные рекомендации, рекламные размещения и продвижение, B2B-аналитика.

### Почему AI можно отложить без потери смысла

AI-резюме имеет смысл только там, где у товара десятки отзывов. На старте их не будет почти ни у кого, и блок всё равно показывал бы «пока мало отзывов». Поэтому выгоднее сначала набрать отзывы, а AI включить, когда у заметной доли сканируемых товаров их станет достаточно. Тогда же это хороший повод для анонса и рекламы. Стоимость включения низкая: лёгкая модель YandexGPT или GigaChat, резюме считается раз на товар при новых отзывах, это сотни рублей в месяц на старте (оценка).

## 11. Сбор базы без партнёров

Самая важная и самая рискованная часть проекта. Приложение, которое на скан отвечает «товар не найден», удаляют после второго раза. Поэтому план такой: **один стартовый город, плотное покрытие, несколько источников сразу.**

### Товары

| Источник | Что даёт | Стоимость | Заметки |
|---|---|---|---|
| Open Food Facts | штрихкод, название, бренд, фото, состав, КБЖУ | бесплатно | есть российские товары, покрытие неполное, точную цифру увидим после импорта. Лицензия ODbL, атрибуция обязательна |
| Ручное добавление через админку | топ-500–1000 самых ходовых товаров сетей стартового города | время | быстрее всего поднимает процент найденных сканов: люди сканируют в основном одно и то же |
| Пользователи (предложение, см. ниже) | новые товары по штрихкоду + фото упаковки | бесплатно, нужна модерация | главный источник роста базы в долгую |
| Национальный каталог (Честный знак) | карточки маркированных товаров по GTIN | нужно проверить условия доступа | молочка, вода, соки и т.д. под маркировкой. Пока гипотеза, не проверено |

Фото товаров с сайтов сетей не берём: это чужой контент, проблемы с авторскими правами.

### Магазины

OpenStreetMap: адреса и координаты магазинов сетей (Пятёрочка, Магнит, Перекрёсток, ВкусВилл и др.) с тегом бренда, бесплатно. Импорт по городу, дальше правки в админке. Лицензия тоже ODbL.

### Цены

Без партнёров это самое сложное, честно.

| Источник | Оценка |
|---|---|
| Цена из отзыва (уже есть в ТЗ) | надёжно, но редко: отзывы пишут не на каждую покупку |
| Быстрая отметка цены после скана (предложение) | один тап «цена на полке такая-то» на карточке. Самый массовый источник, растёт вместе с аудиторией |
| Чеки через QR (ФНС) | названия и цены из чека, но без штрихкодов, нужно сопоставление. Сложно, после MVP |
| Парсинг сайтов сетей и доставок | технически возможно, но риск по условиям сайтов и праву на базы данных (ст. 1334 ГК РФ), плюс онлайн-цена не всегда равна цене на полке. Не строим на этом бизнес, максимум точечный адаптер после проверки юристом |

Каждая цена хранит источник, время и уровень доверия, поэтому в UI всегда честно видно «обновлено вчера, по данным покупателей».

### Два предложения сверх ТЗ

Оба нужны именно для сбора базы, без них она будет расти очень медленно. Делаю только после твоего согласия:

1. **«Добавить товар»** на экране «не найден»: штрихкод уже считан, пользователь фотографирует лицевую сторону, состав и КБЖУ. Товар уходит в очередь модерации, данные вносятся вручную в админке, позже распознаются AI.
2. **«Отметить цену»** на карточке: одно поле и выбор магазина из ближайших.
